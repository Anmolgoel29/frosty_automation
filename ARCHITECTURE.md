# Architecture

Detailed module documentation for OpenOutreach. See `CLAUDE.md` for rules and quick reference.

## Entry Flow

`manage.py` — stock Django management entrypoint. Bare `python manage.py` (no args) defaults to `rundaemon`.

### `rundaemon` management command (`management/commands/rundaemon.py`)

Startup sequence:
1. **Configure logging** — DEBUG level, suppresses noisy third-party loggers (urllib3, httpx, pydantic_ai, openai, playwright, etc.).
2. **Ensure DB** — `migrate --no-input`.
3. **Onboard** — checks `missing_keys()`; if incomplete, applies `collect_from_wizard()` (non-interactive: loads `config.json` from data dir / cwd / `~/.openoutreach/`, else defaults). If required fields are still missing, exits with a clear error — the Docker supervisor retries after you finish onboarding via the admin panel or `config.json`.
4. **Validate** — `expensive_llm_api_key` and `cheap_llm_api_key` both set, active `LinkedInProfile`, at least one campaign.
5. **Sessions** — one `get_or_create_session(profile)` per *active* `LinkedInProfile`, keyed by profile pk, each with its own default campaign (first non-freemium available). Accounts attached to no campaign are skipped with a warning. The daemon drives one browser per account.
6. **Newsletter** — Auto-subscription is disabled for self-hosted runs; no outbound signup call is made.
7. **Run** — `run_daemon(session)`.

The HuggingFace-hosted freemium campaign kit (download + GP-model import) has been removed; the daemon only uses locally configured campaigns.

Docker `start` script (`compose/linkedin/start`) sets up Xvfb + VNC, runs `migrate` and an optional `createsuperuser --noinput` (from `DJANGO_SUPERUSER_*` env), then supervises two long-lived processes: the admin web server (`uvicorn webadmin.main:app --host 0.0.0.0 --port 8000`, always up — see "Admin panel (webadmin/)" below) and `rundaemon` (restarts on exit). Both connect to the same Postgres `db` service, which handles their concurrent writes natively (no busy-timeout workaround, unlike the old SQLite setup).

### Other management commands

- `onboard` — standalone onboarding (interactive or `--non-interactive` with `--config-file` / individual flags).
- `add_seeds` — add seed LinkedIn profile URLs to a campaign.
- `add_profile --email … --password … [--campaign NAME …] [--user handle] [--update-password] [--list]` — attach another LinkedIn account to one or more campaigns, so they prospect it together. Delegates to `onboarding.ensure_account()` (the single write path for accounts, shared with onboarding): creates the `LinkedInProfile` plus a dedicated Django user, or reuses an existing user with `--user` (several accounts may share one, inheriting its `Campaign.users` membership). Idempotent — an existing account keeps its stored password unless `--update-password` is passed (which also clears `cookie_data` so the next login is fresh). `--campaign` defaults to every campaign. `--list` prints the accounts per campaign. The running daemon picks the new account up on its next idle cycle; no restart needed.
- `migrate_sqlite_to_postgres` — one-time upgrade helper for installs that still have data in `data/db.sqlite3`. Works even when the legacy DB is behind on migrations. It (1) copies the SQLite file to a throwaway working copy, (2) in a subprocess with that copy as the **default** DB (via the `OPENOUTREACH_LEGACY_SQLITE` env var, see `django_settings.py`) runs `migrate` to bring it up to the current schema — a subprocess so the historical data migrations, which query via `Model.objects` without `.using(...)`, replay against the SQLite instead of Postgres — then `dumpdata`s it with `--natural-foreign --natural-primary`, (3) runs `migrate` against Postgres, (4) `loaddata`s the export in. Natural keys make FKs into contenttypes/permissions resolve against Postgres's own rows (not collide on raw ids) and match the auto-created superuser by username. Finally it prints a per-table row-count comparison (legacy vs Postgres) so you can confirm nothing was dropped, and keeps the exported JSON in `data/` as a backup.
- `migrate_postgres_to_remote --source-url <url> --target-url <url>` — copy all data from one Postgres into another (e.g. Supabase → Neon/RDS/self-hosted, or hosted → local). Both endpoints are explicit flags: `--source-url` (defaults to the ambient `DATABASE_URL`/`POSTGRES_*`) is read from, `--target-url` (or the `TARGET_DATABASE_URL` env var) is written to. Same dump/migrate/load shape as `migrate_sqlite_to_postgres`, but both sides are Postgres and no schema-catch-up copy is needed. It registers **both** URLs as connection aliases via `_register_alias(alias, url)` — `postgres_source` and `postgres_target`, each a fully-defaulted dict built from `django_db_config(url)` (Django only fills per-alias defaults like `OPTIONS`/`TIME_ZONE`/`CONN_MAX_AGE` in `configure_settings`, which is cached and never re-runs for an alias injected afterward, so the dict must carry them) — so every in-process phase runs against those aliases and nothing depends on how the ambient `default` DB happens to be configured. Then: (1) `dumpdata --database postgres_source` with `--natural-foreign --natural-primary`, excluding `contenttypes`/`auth.permission`; (2) runs `migrate` against the target in a subprocess with the target as **default** (via a `DATABASE_URL`-overridden env, POSTGRES_* stripped so a stray fallback can't shadow it) — a subprocess because the historical data migrations query `Model.objects` without `.using()`; (3) **streams** the export into the `postgres_target` alias in-process (not the opaque `loaddata` subprocess) via a faithful port of loaddata's inner loop — `constraint_checks_disabled` during inserts, `save(using=target)` per object, deferred natural-key forward references saved at the end, `check_constraints`, then `sequence_reset_sql` so the target's PK sequences don't collide with future inserts — emitting **live timestamped progress**: a per-model row tally as each model completes and a heartbeat every ~2s (`loaded/total`, %, rows/s, ETA, current model); (4) prints a source-vs-target row-count comparison over the two aliases. All phases log through a timestamped `_log()`. Refuses to run if source and target resolve to the same host/port/db. The target should be an empty/fresh DB (its own rows for loaded tables would collide on PK). Keeps the exported JSON in `data/` as a backup. Passwords are redacted in the printed source/target lines. (loaddata is per-row over the network, so this is inherently slow on a high-latency remote link — the progress output is there so a long phase 3 is legible rather than silent.)

## Onboarding (`onboarding.py`)

`OnboardConfig` — pure dataclass with all onboarding fields. Two constructors:
- `OnboardConfig.from_json(path)` — from JSON file (cloud / non-interactive).
- `collect_from_wizard()` — interactive questionary wizard (needs TTY), only asks for `missing_keys()`.

Single write path: `apply(config)` — idempotent, creates missing Campaign, LinkedInProfile, env vars, and legal acceptance. Four components:

1. **Campaign** — name, product docs, objective, booking link, seed URLs. Creates `Campaign` with M2M user membership.
2. **LinkedInProfile** — email, password, newsletter, rate limits. Django username from email slug.
3. **LLM config** — `CHAT_LLM_PROVIDER`/`CHAT_LLM_API_KEY`/`CHAT_AI_MODEL`/`CHAT_LLM_API_BASE` and `TASK_LLM_PROVIDER`/`TASK_LLM_API_KEY`/`TASK_AI_MODEL`/`TASK_LLM_API_BASE` → write to the two independent role groups on the `SiteConfig` singleton in DB.
4. **Legal notice** — per-account acceptance stored as `LinkedInProfile.legal_accepted`.

## Multi-Account Campaigns

A campaign runs on **every** active `LinkedInProfile` whose Django user is in `Campaign.users` — `Campaign.active_profiles()` returns them ordered by pk, which is the round-robin rotation order. `LinkedInProfile.user` is a plain FK (not one-to-one, as it was before): several LinkedIn accounts may share a Django user and thereby its campaign membership, which is what makes "add a second account to this campaign" a single form in the admin panel.

The split between shared and owned work sits at exactly one place, the connect step:

- **Shared (campaign-wide)** — search, enrichment, qualification, fit-score promotion. `Lead` rows are global, `Deal` rows are campaign-scoped, neither is per-account. Whichever account's connect task happens to be running drives the pipeline. `get_qualified_profiles()` is deliberately *not* account-scoped.
- **Owned (per-account)** — from READY_TO_CONNECT onwards. `pipeline/allocation.py:allocate_ready_deals(campaign)` deals un-owned READY_TO_CONNECT deals out one per account in rotation, advancing `Campaign.assignment_cursor` (persisted, so the rotation survives restarts and doesn't restart at the first account for every new lead) and stamping `Deal.assigned_profile`. `get_ready_to_connect_profiles()` filters to `assigned_profile=session.linkedin_profile`, so `find_ready_candidate` — and therefore `handle_connect` — only ever sees this account's own leads.

Ownership is sticky and never crosses over. This is a correctness constraint, not a fairness one: a pending invite and the message thread it turns into exist only on the account that sent them, so a follow-up from a different account would be sent into a conversation that doesn't exist. Consequences:

- `set_profile_state()` claims an un-owned deal for the acting account when it enters PENDING or CONNECTED (`_CLAIMING_STATES`). This covers leads that never pass through allocation — seeded QUALIFIED deals, and profiles found to be already connected/invited on this account.
- A deal bounced back to QUALIFIED (follow-up send failure) keeps its owner, so it never re-enters the shared pool.
- `reclaim_unreachable_deals(campaign)` returns *un-contacted* leads (QUALIFIED / READY_TO_CONNECT) held by a deactivated or detached account to the pool for re-allocation. Contacted deals are deliberately left stranded; `_seed_deal_tasks` counts them and logs a warning naming the campaign.
- Rate limits are per account (`can_execute` / `ActionLog` are keyed by `linkedin_profile`), so one account hitting its daily connect cap only stalls its own connect loop.

### Parallel execution

Each account gets a worker thread (`daemon._AccountWorker`) with its own browser, so they search and connect simultaneously rather than taking turns. The Playwright sync API is thread-affine: a session's Playwright objects belong to the worker that created them, which is why the supervisor signals a worker to stop instead of calling `session.close()` across threads, and why each worker tears down its own browser in a `finally`.

The main thread is the supervisor. Every `supervisor_interval_seconds` (60) it runs `sync_sessions()`, respawns any dead worker (`_sync_workers`), and calls `reconcile(sessions)`. Reconciliation has exactly one writer by construction; workers only ever enqueue their own follow-on tasks.

What makes this safe:

- **Task claiming** — `TaskQuerySet.claim_for(profile_id)` does `SELECT … FOR UPDATE SKIP LOCKED` and flips the row to RUNNING inside the same transaction, so two workers can't hold one task. Tasks are already partitioned by `linkedin_profile_id`, so contention is near zero; `SKIP LOCKED` means a worker never blocks on a row someone else took. Among an account's own due tasks, claiming isn't pure FIFO: a `Case/When` annotation orders by priority first — `follow_up` (an actual message to a connected lead) and `check_pending` (polling a pending invite — the path that discovers an acceptance) tied at top priority, `connect` (a connection request, and that account's own search/scan loop when its ready pool is empty) last — then `scheduled_at` as the tiebreaker within a priority band. So a worker with a due connect and a due follow_up or check_pending always handles the messaging-adjacent one first. Relatedly, `on_deal_state_entered` (`tasks/scheduler.py`) enqueues the CONNECTED → follow_up task with `delay_seconds=0`, so the moment a connect/check_pending task observes an accepted invite, the first message is due immediately rather than after the generic 10s enqueue delay.
- **Task creation** — `scheduler._TASK_LOCK` (an `RLock`, re-entrant because `reconcile` holds it across its enqueues) wraps the check-then-insert in `_insert_task`. All task creation already funnels through that one function, so a process-wide lock is sufficient and avoids a partial unique index over JSON payloads. Without it two threads both miss an existing row and create a duplicate `follow_up` — which means messaging the same lead twice.
- **Stale-task recovery** — `recover_stale_running_tasks()` is **startup-only**. Once workers are alive, RUNNING means "a thread is executing this", so blanket-resetting RUNNING rows would hand live work back to the queue. At startup no worker exists, so any RUNNING row is an orphan from a crashed process. Correspondingly, reconcile's seeders call `has_live_task()`, which counts PENDING *and* RUNNING, so it never stacks a second task on one mid-execution. The enqueue dedup deliberately still ignores RUNNING, because handlers self-reschedule while their own task is running.
- **Qualification** — `pipeline/locks.py:campaign_lock(campaign)` serialises `run_qualification`, `promote_to_ready`, and keyword generation. A campaign has one shared unlabelled pool; without the lock two accounts could pick the same unlabelled lead (duplicate LLM spend at both cascade stages, then a `unique_deal_per_campaign` violation). Candidates are re-read *inside* the lock so the second account through sees the first one's Deal. The slow browser-bound work stays outside it.
- **Search division** — `search._claim_keyword` claims a `SearchKeyword` with `SKIP LOCKED` and marks it used in one transaction. The keyword queue is campaign-wide and every account pulls from it, so the accounts cover different searches instead of repeating each other. This is the whole mechanism by which search workload is divided.
- **Geographic targeting** — `Campaign.search_locations` is a hand-entered JSON list of `{"name", "urn"}` pairs (e.g. `{"name": "India", "urn": "102713980"}`), applied as an OR facet to every prospecting search so the campaign only surfaces people in those regions. `Campaign.geo_urns()` reduces it to the bare numeric ids LinkedIn's `geoUrn` facet wants and `geo_labels()` gives the names for log lines; `actions/search.py:_initiate_search` renders them as `geoUrn=["102713980","103644278"]` and flips `origin` from `GLOBAL_SEARCH_HEADER` to `FACETED_SEARCH`, which is what LinkedIn's own UI sends once any filter is on. An empty list means no facet and no origin change — an unconfigured campaign searches worldwide exactly as before. `_paginate_to_next_page` rebuilds the URL from the current one, so the facet carries to page 2+ on its own.

  Three deliberate choices. **The ids are entered by hand, never generated**: they are opaque numbers an LLM will confidently invent, so keyword generation is left completely untouched — the LLM writes queries, the operator says where. Get one by running the search in LinkedIn's UI with a location filter applied and copying `geoUrn` out of the address bar. **`geo_urns()` is liberal in what it accepts** (a `{"name","urn"}` pair or a bare id; `"102713980"` or `"urn:li:fsd_geo:102713980"`) and skips malformed entries with a warning rather than raising, because these are pasted by hand and one typo shouldn't stop the campaign searching on the rest. **The facet is passed as an argument, not read off `session.campaign`** inside `_initiate_search`: prospecting should respect the targeting, but `_simulate_human_search` looks up a *named individual* through the same function, and filtering that by region would simply fail to find someone who lives elsewhere.
- **Concurrent discovery** — two accounts searching different keywords regularly land on the same person, so `create_enriched_lead` and `Lead.get_profile` treat `IntegrityError` on the `public_identifier`/`urn` unique constraints as "someone else won the race", not a crash.
- **Pacing** — `_HumanRhythmBreak` is per worker. `_StartSpacer` additionally holds a jittered `account_stagger_{min,max}_seconds` (20–60s) gap between any two accounts *starting* a task. Tasks still overlap — that is the point of running in parallel — but the accounts don't fire their first request in the same second repeatedly, which is the part that correlates them from a shared IP.
- **Log readability** — worker threads are named after their account and `ColoredFormatter` tags each line with the thread name, so interleaved output stays attributable.

A bad LLM config (`ModelHTTPError`) sets the global stop event, since it breaks every account rather than one. Each worker closes its Django DB connection on exit.

### Watching each account's browser

Every account renders on its own Xvfb display, `:100 + profile_id` (`vnc.py:display_for`), spawned on demand by `session.ensure_display()` → `_ensure_xvfb` and gated on `OPENOUTREACH_PER_ACCOUNT_DISPLAY` (set by `compose/linkedin/start`; off by default so local development keeps using the developer's real X server). `launch_browser(display=…)` passes it through as `env={**os.environ, "DISPLAY": display}` — Playwright's `env` *replaces* the browser's environment rather than merging, so the current one has to be copied in.

`_ensure_xvfb`'s liveness check reads the PID recorded in `/tmp/.X<n>-lock` and confirms that process is actually alive (`os.kill(pid, 0)`), rather than trusting the lock file's mere existence. A plain existence check breaks across an unclean container restart: a container that gets SIGKILLed (OOM, a `docker stop` timeout — `restart: unless-stopped` recreating a killed container preserves its writable layer, so `/tmp` survives) never lets Xvfb remove its own lock on the way out, so the stale file persists into the next run and looks identical to a live one. `_ensure_xvfb` would then skip spawning a real Xvfb entirely, and every consumer of that display fails downstream — x11vnc's `XOpenDisplay failed`, then Chromium's `Missing X server or $DISPLAY` / `TargetClosedError`. On a stale lock (dead PID) it now removes both `/tmp/.X<n>-lock` and the `/tmp/.X11-unix/X<n>` socket file before starting a fresh Xvfb — the socket file alone would otherwise make Xvfb's own bind fail with "already active for display".

`launch_browser` wraps everything after `sync_playwright().start()` in a try/except that calls `playwright.stop()` before re-raising. Without it, any failure between `.start()` and the function returning (e.g. the Chromium launch failure above) leaks the Playwright driver connection — and because Playwright's sync-API dispatcher runs on a greenlet sharing the calling OS thread rather than a separate one, a leaked connection's `run_until_complete` stays suspended mid-flight, which leaves that thread's asyncio "currently running loop" marker stuck set. Every *subsequent* `sync_playwright()` call on the same worker thread then fails immediately with `"using Playwright Sync API inside the asyncio loop"` instead of retrying — permanently breaking that account (each account has exactly one persistent worker thread — see "Parallel execution") until the whole daemon process restarts, regardless of what caused the original failure. Reproduced directly against the Playwright sync API outside Docker (a failed `.chromium.launch()` without `.stop()` poisons a second `sync_playwright().start()` on the same thread; calling `.stop()` first does not).

Behind those displays there is a single VNC server on the existing ports (6080 noVNC / 5900 native). `compose/linkedin/start:vnc_follow_selected_display` polls `vnc.py:DISPLAY_CONTROL_FILE` and restarts x11vnc against whichever display it names, tracking the pid rather than using `pkill` (procps is not guaranteed in the base image, and a silent `pkill` failure would strand the viewer). With nothing selected it picks the **lowest live per-account display**, never `:99` — `:99` is a bare desktop that no browser draws on, so defaulting there shows a working stream of nothing. The admin panel switches accounts by rewriting the control file (`webadmin/admins.py:_watch_browser`, one account at a time); the noVNC tab reconnects on its own with `?reconnect=1`.

A VNC server per account was rejected: its ports would have to be published before the container starts, which contradicts adding accounts to a running daemon. Note that `/start` is baked into the image (`COPY ./compose/linkedin/start /start`) and is *not* under the `.:/app` bind mount, so changes to it require `make build`. `daemon.sync_sessions(sessions)` re-reads the active-account roster from the DB on every idle cycle (mutating the dict in place, re-binding each `LinkedInProfile` row and invalidating the `campaigns` cached_property), so an account added or deactivated in the admin joins or leaves the rotation within ~a minute instead of at the next restart. Sessions dropped from the roster have their browser closed.

## Profile State Machine

`enums.py:ProfileState` (TextChoices) values ARE CRM stage names: QUALIFIED, READY_TO_CONNECT, PENDING, CONNECTED, COMPLETED, FAILED. Pre-Deal states: url_only (Lead row exists, `coarse_scraped_at` is null), enriched (coarse fields populated via `create_enriched_lead`/`ensure_coarse_fields`). `Lead.disqualified=True` = permanent account-level exclusion. LLM rejections = FAILED Deals with wrong_fit outcome (campaign-scoped).

`crm/models/deal.py:Outcome` (TextChoices): converted, not_interested, wrong_fit, no_budget, has_solution, bad_timing, unresponsive, unknown. Used by `Deal.outcome`.

## Task Queue

Persistent queue backed by `Task` model. Every row carries `linkedin_profile` — the account that must execute it — which is what partitions the queue between the parallel workers. Per-worker loop in `daemon._AccountWorker`: `seconds_until_active()` guard pauses outside active hours/rest days → `Task.objects.claim_for(profile_id)` atomically takes this account's next due task and marks it RUNNING → `_StartSpacer.wait_turn()` → set campaign on session → dispatch via `_HANDLERS` dict → COMPLETED/FAILED. A worker with an empty queue simply waits (polling in `QUEUE_POLL_INTERVAL` slices so the admin's "Run now" lands within ~60s); reconciliation is the supervisor's job. Failures captured by `failure_diagnostics()` context manager.

Task creation is centralized in `linkedin/tasks/scheduler.py`. No other module inserts Task rows. The module exposes three layers: (1) low-level `enqueue_connect`/`enqueue_check_pending`/`enqueue_follow_up`, each taking the executing account and deduping against existing PENDING rows with the same `(task_type, linkedin_profile, payload keys)`, (2) a state-transition hook `on_deal_state_entered(deal)` fired by `set_profile_state()` that picks the right task for the new state and routes it to `deal.assigned_profile` (warning + no task if the deal has no owner), and (3) `reconcile(sessions)` which walks CRM state and recreates missing tasks. `reconcile` takes the `{profile_pk: AccountSession}` map; per campaign it reclaims/allocates ready leads, seeds one connect task per running account (`_seed_connect_tasks`), and re-creates deal tasks only for deals whose owning account is in the map (`_seed_deal_tasks`).

The daemon calls `reconcile()` whenever the queue has no ready task — startup and every idle cycle. This is the retry mechanism: a handler that crashes mid-execution leaves a FAILED task with no successor, and the next idle cycle re-creates it from the Deal's state. `AuthenticationError` (401) triggers `session.reauthenticate()` then marks the task FAILED; reconcile picks it up.

When idle, the daemon doesn't sleep for the full delay until the next `scheduled_at` in one block — it polls in `QUEUE_POLL_INTERVAL` (60s) slices, rechecking `Task.objects.seconds_to_next()` between each. This bounds how long a task rescheduled to run sooner (e.g. via the Task admin's "Run now" action — see "Admin panel (webadmin/)" below) takes to actually start — at most ~60s, regardless of how far out it was originally scheduled.

Three task types (handlers in `linkedin/tasks/`, signature: `handle_*(task, session)`):

1. **`handle_connect`** — Per account: each account working a campaign has its own connect task and its own rate-limit budget. Uses `ConnectStrategy` dataclass with `find_candidate()` from `pools.py`, which only yields leads allocated to this account. Unreachable detection after `MAX_CONNECT_ATTEMPTS` (3).
2. **`handle_check_pending`** — Per-profile. Exponential backoff with jitter. On acceptance → enqueues `follow_up`.
3. **`handle_follow_up`** — Per-profile. Syncs the conversation (`db/chat.py:sync_conversation`) *before* evaluating `_unanswered_count`/`_too_soon_to_nudge` — both read local `ChatMessage` rows, so gating on them pre-sync would judge a reply that already arrived on LinkedIn by stale local state (and just re-enqueue without ever seeing it; this also made the Task admin's "Run now" action a no-op against a fresh reply). `_too_soon_to_nudge` requires `unanswered_count * MIN_DAYS_PER_UNANSWERED` (3) days of silence since the last *outgoing* message — it returns `False` immediately once the most recent message is an incoming reply, so a synced reply always clears the cooldown. After the gates pass, calls `run_follow_up_agent()` (assumes the caller already synced) which returns a `FollowUpDecision` (structured output: `send_message`/`mark_completed`/`wait`). Handler executes the decision deterministically. On `send_message`, it syncs the conversation *again* right after the send succeeds: `actions/message.py:send_raw_message` only drives the browser/Voyager send, it never writes a `ChatMessage` row — that only happens via `sync_conversation`'s re-fetch-and-diff of the whole thread. Without the post-send sync, the message just sent has no local row (and so is invisible to the dashboard's message counts, `chat_summary`, and the very cooldown gates above) until the *next* scheduled `follow_up` for that lead happens to run, which — per `decision.follow_up_hours` or the 24h/3-9d backoff paths — can be hours to days away. This was a real bug (dashboard undercounting recently-sent messages) fixed by adding the second sync call.

## Database Query Budgets

The daemon is a loop that never ends, so what matters is not how fast a query is but whether its *count* grows with the pipeline. Measured before/after on the hot paths (`tests/test_db_query_budget.py` keeps them honest by asserting the count is flat as the data grows, rather than asserting a magic number):

| Path | Before | After | Runs |
|---|---|---|---|
| `reconcile()` @ 50 active deals | 163 | 11 | every 60s, forever |
| `promote_to_ready()` @ 50 QUALIFIED | 51 | 1 | every backfill iteration |
| `get_ready_to_connect_profiles()` @ 50 ready | 50 | 1 | every connect task |
| `fetch_next_qualification_candidate()` | 2 (unbounded rows) | 1 (single row) | once per qualification |

The changes behind those numbers:

- **`reconcile()`** — was two queries per active deal (an existence check, then an insert), which is what made DB volume grow with the pipeline rather than stay flat. Now `_live_task_keys(campaign_id)` reads every pending-or-running task for the campaign once into a set of `(task_type, profile_id, public_id)` keys, `_seed_connect_tasks`/`_seed_deal_tasks` test membership in memory and append to a list, and one `bulk_create` writes everything missing. They no longer route through `on_deal_state_entered` (which enqueues one at a time); the backoff jitter and payload shapes are reproduced inline to match `enqueue_check_pending`/`enqueue_follow_up`.
- **`promote_to_ready()`** (`pipeline/ready_pool.py`) — one bulk `UPDATE ... WHERE state=QUALIFIED AND fit_score >= threshold`, replacing what used to be a Python-side ranking pass over every QUALIFIED profile's embedding. There's no per-profile scoring step left to budget: `fit_score` was already computed once, at qualification time, by the expensive LLM call — promotion just filters on the stored column.
- **`get_ready_to_connect_profiles()`** (`db/deals.py`) — orders by `fit_score` descending at the DB level (an indexed column comparison), so ranking an account's ready pool for connect order costs the same one query regardless of pool size. There's no separate ranking function to call anymore.
- **`fetch_next_qualification_candidate()`** (`pipeline/qualify.py`) — a single-row query (`order_by("creation_date").first()`), not a windowed batch. The old batched-and-capped version existed so the GP's acquisition strategy had a representative sample to score; without a statistical model in the loop there's no batch to score at all — `run_qualification` only ever needs the one lead it's about to process. `has_qualification_candidates()` is the EXISTS variant for callers that only need yes/no.
- **`set_profile_state()`** — saves with `update_fields`. `Deal` carries two JSON fact lists (`profile_summary`, `chat_summary`) that can be kilobytes each; a bare `save()` re-sent them on every state transition.
- **`allocate_ready_deals()`** — groups the rotation by owner and issues one UPDATE per account instead of one per lead.
- **`_sync_from_api()`** (`db/chat.py`) — was `update_or_create` per message (a SELECT plus a write each) on a thread that is re-fetched in full every sync. Now one query collects the already-known `linkedin_urn`s and `bulk_create` inserts only the new rows; LinkedIn messages are immutable once sent, so there is nothing to update on the ones already stored.
- **`AccountSession._maybe_refresh_cookies()`** — throttled to one read per `COOKIE_CHECK_INTERVAL` (300s). It ran on every `ensure_browser()` — which fires per profile visit, per scrape, per message — and each call re-read the whole cookie JSON blob to check an expiry measured in days.

Deliberately *not* optimised: `can_execute()` keeps its `refresh_from_db`, so a rate limit edited in the admin takes effect on the very next check (covered by `tests/test_action_log.py::TestDynamicLimitChanges`). It runs once per rate-limited task rather than in a loop, so the guarantee is worth more than the query.

## Qualification Pipeline

A two-stage LLM cascade — no statistical model, no active learning, no per-campaign state to warm-start or go stale.

1. **Candidate selection** — `pipeline/qualify.py:fetch_next_qualification_candidate()` pulls the single oldest Lead in the campaign not yet dealt (`order_by("creation_date").first()`). Plain FIFO: with no acquisition strategy deciding which lead is most "informative" to label next, there's nothing left to select among — every candidate gets the same treatment in the order it was discovered.
2. **Stage 1 — cheap disqualify-only prefilter** (`ml/qualifier.py:qualify_cheap()`, `role="cheap"`) — a fast/cheap LLM call over exactly two fields cached on `Lead` at discovery time: `headline` and `about` (the profile's About section, stored untruncated). Both are populated for free in `db/leads.py:create_enriched_lead()` from the profile dict search enrichment already scraped, so this stage makes **no network call at all**. The prompt (`qualify_lead_cheap.j2`) is deliberately conservative: it's told those are the only two fields it has, asked to set `disqualify=True` only when highly confident the profile is an obvious mismatch (obviously wrong industry, obviously wrong seniority/function), explicitly told *not* to reject for anything that would need the experience/company/location it cannot see, and to pass through on any real doubt or when both fields are empty. A cheap-stage disqualify writes the same FAILED/`wrong_fit` Deal as any other rejection (`create_disqualified_deal`) and **the dossier scrape below never runs** — which is the point of the stage, since that scrape is several LinkedIn reads.

   **Legacy-row repair.** Those two columns arrived with this cascade, so every lead discovered under the old GP qualifier — plus url-only seeds (`setup/seeds.py`, which creates a `Lead` with nothing but a URL) — carries the blank column default. Blank fields are exactly the case the prompt is told to pass through, so for those rows the cheap stage degrades into a no-op that still costs an LLM call and still lets the full dossier scrape run. `Lead.coarse_scraped_at` (nullable timestamp; null = "these coarse fields never came from a real scrape") is the marker that distinguishes them: `create_enriched_lead` stamps it on every new lead, and `db/leads.py:ensure_coarse_fields(session, lead)` — called from `_run_qualification_locked` immediately before `qualify_cheap` — gives any un-stamped row exactly one repair scrape (`lead.get_profile(session)` → `_coarse_fields_from_profile`), then stamps it. The stamp is what bounds the work: it is written even when the re-scrape legitimately yields an empty About, so a genuinely bare profile is never re-scraped a second time. A row that already holds coarse data is stamped without scraping; an unreachable profile (private/deleted) leaves the marker null, logs a warning and falls through — `build_dossier_text` hits the same unreachable profile moments later and disqualifies it with "profile not reachable", so it exits the pool anyway. Net effect: the cheap stage is still network-free in steady state, and the repair cost drains away as the legacy backlog does. Clearing `coarse_scraped_at` on a Lead in the admin forces a fresh re-scrape of that lead's coarse fields.
3. **Stage 2 — expensive full-dossier qualify + fit score** (`ml/qualifier.py:qualify_with_llm()`, `role="expensive"`) — whatever survives stage 1 gets a full dossier built (see "Qualification Dossier" below) and the qualify/reject call against `qualify_lead.j2`, which also asks for a 1-5 `fit_score` self-rating. The prompt states explicitly what the dossier contains and how to read missing values, and tells the model to weigh the current role and current company most heavily. `qualified=True` creates a QUALIFIED Deal with `Deal.fit_score` set; `qualified=False` creates a FAILED/`wrong_fit` Deal exactly like a cheap-stage rejection.
4. **READY_TO_CONNECT gate** — `pipeline/ready_pool.py:promote_to_ready(session, threshold)` bulk-promotes QUALIFIED deals with `fit_score >= threshold` (`CAMPAIGN_CONFIG["min_fit_score"]`, default 4) to READY_TO_CONNECT. It re-evaluates the *entire* QUALIFIED backlog against the current threshold on every call — not just deals labelled since the last promotion pass — so changing `min_fit_score` mid-campaign takes effect immediately on leads already sitting QUALIFIED, not only on future labels.
5. **Connect-order ranking** — `db/deals.py:get_ready_to_connect_profiles()` orders an account's allocated READY_TO_CONNECT pool by `fit_score` descending, so the strongest-rated leads get contacted first. This is a plain indexed `ORDER BY`, not a scoring pass, so there's no separate "rank the pool" function anymore.

**Cost accounting.** Every Deal the cascade creates is stamped with `qualification_stage` — `"cheap"` if stage 1 disqualified it (no dossier scrape), `"expensive"` if it reached stage 2 (a dossier build that came back empty, i.e. "profile not reachable", still counts as `"expensive"` — the scrape was attempted and paid for). `create_disqualified_deal()` takes the stage as a parameter, threaded from each of its three call sites in `pipeline/qualify.py`; `promote_lead_to_deal()` hardcodes `"expensive"` since it has only one caller. Deals created outside the cascade (anything seeded/promoted manually) leave the column null. It's a pure accounting field — nothing reads it back into qualification decisions — surfaced on the admin dashboard as the "Disqualified — Cheap Stage" / "Reached Expensive Stage" tiles and daily-funnel columns (see Admin panel below), as a proxy for how much of the several-reads-per-lead dossier cost the cheap prefilter is actually saving.

**Why no GP/BALD**: the previous system fit a Gaussian Process Regressor on FastEmbed profile-text embeddings, refit on *all* accumulated labels every time (no decay, no windowing), and used it for three things — deciding which unlabelled lead to spend the one LLM call on next (BALD in explore mode, P(f>0.5) in exploit mode), gating QUALIFIED → READY_TO_CONNECT on posterior confidence, and ranking the ready pool by posterior mean. The LLM was already the sole source of qualify/reject truth in that system too — the GP never overrode it, only decided which candidate reached it and re-ranked afterward. The problem was mid-campaign steerability: a model refit on unweighted all-time history has no way to "forget" labels that reflected a since-changed `campaign_objective`/`product_docs`, so a pivot meant fresh LLM labels fighting stale embedding-space geometry — flipping explore/exploit mode, destabilizing the majority-class subsampling — until enough new labels statistically dominated. A pure LLM cascade has no such memory: a prompt edit takes effect on the very next lead. The tradeoff accepted going in: the GP's cheap re-ranking of an already-qualified pool without any further LLM calls is now replaced by `fit_score`, a value fixed once at qualification time rather than continuously recomputed — a reasonable proxy since it's the same expensive model's own judgment, just captured once instead of re-derived from an embedding on every read.

**GP qualifier removal.** `linkedin/ml/qualifier.py` used to still carry `KitQualifier` and the GP-numerics helpers it depended on (`_gpr_predict`, `_prob_above_half`, `_rank_by_score`, `_load_profile_embeddings`), backing pre-trained kit models for freemium campaigns — a code path that was already unreachable (freemium kit download/import was disabled) with zero live callers. That class, its GP numerics, `linkedin/ml/hub.py` (the HuggingFace Hub kit downloader), `linkedin/ml/embeddings.py` (the fastembed text-embedding wrapper — the only other thing that ever talked to HuggingFace, via the `BAAI/bge-small-en-v1.5` model download), `linkedin/setup/freemium.py`, and `linkedin/pipeline/freemium_pool.py` have all been deleted, along with `Lead.get_embedding()`/`embed_from_profile()`/`embedding_array` and `db/deals.py:create_freemium_deal()`. `Lead.embedding` remains as a DB column so existing rows keep whatever was written before removal, but nothing computes or reads it anymore, and no new HuggingFace/fastembed network requests are made by any code path. `Campaign.is_freemium`/`action_fraction` remain as legacy fields for the same reason (see "Entry Flow" above and "Campaign" below).

### Qualification Dossier (`ml/dossier.py`)

What stage 2 actually reads. Split in two so the rendering is testable without a browser: `collect_dossier(session, lead)` does the scraping, `render_dossier(dossier)` produces the text, `build_dossier_text()` chains them.

**Collected** — the profile itself via `Lead.get_profile()` (headline, full About, complete experience history, education); the lead's follower count (a DOM scrape, not a Voyager read — see below); the lead's 3 most recent posts; and then, for **every company the lead currently works at**, that company's page (About/description, industry, employee count, follower count, tagline) plus its 3 most recent posts. "Currently works at" is `current_companies()`: a position whose `date_range.end` is absent — a missing `date_range` entirely also counts, since LinkedIn omits it for roles with hidden dates and nothing in the payload says the role ended. Results are deduped on the company page slug, so a lead promoted twice inside one employer is one scrape, not three; a lead genuinely active at three companies gets all three. The slug comes from `Position.company_url` (added to the parser for exactly this), via `api/enrichment.py:company_universal_name()` which handles `/company/`, `/school/` and `/showcase/` URLs.

**Rendered** — explicitly labelled plain text, one `Field name: value` per line under `=== SECTION ===` headers, e.g. `Company industry: Software Development`, `Currently active in this role: yes`. The point is that the model never has to infer what a bare line of text is. Values LinkedIn didn't return render as `unknown` / `(empty)` / `(none)` / `none found`, and `qualify_lead.j2` explicitly tells the model to treat those as missing information rather than negative signals. **Nothing is truncated** — whole About sections, whole role descriptions, full post bodies. Deliberately *not* reusing `ml/profile_text.py:build_profile_text()`, which lowercases and concatenates without labels: that shape is right for embeddings and wrong for a prompt.

**Extra Voyager reads** live in `api/enrichment.py`, separate from `api/client.py` because they are all optional: `fetch_member_posts` (`/identity/profileUpdatesV2?q=memberShareFeed`), `fetch_company` (`/organization/companies?q=universalName` with the `WebFullCompanyMain` decoration), `fetch_company_posts` (`/feed/updates?q=companyFeedByUniversalName`). Every one is **fail-soft**: returns `None`/`[]` and logs a warning rather than raising, because a private company page, a member with posting disabled, or an endpoint LinkedIn has quietly moved should degrade the dossier — not abort qualification of a lead who might be perfect. `AuthenticationError` is the sole exception and always propagates, since a 401 means the session is dead and the daemon must re-authenticate. Post-body extraction (`_walk_post_texts`) *walks* the response for the stable inner `commentary.text.text` shape rather than matching an exact path, because the wrapper around it differs per feed surface and changes over time. These endpoints are LinkedIn-internal and unversioned — `python -m linkedin.api.enrichment --profile <public_id> --company <slug>` probes them against a live session when one starts returning empty.

**Follower count is a DOM scrape, not a Voyager read.** `fetch_follower_count(session, profile)`, same module, used to hit `/identity/profiles/{id}/networkinfo`; that endpoint now returns HTTP 410 Gone, and the field was never on the main profile decoration either — LinkedIn moved it behind GraphQL. Reverse-engineering an unversioned GraphQL query id for one optional number wasn't worth it, so this navigates the browser to the profile page instead and reads the top card's "X followers" text — matched by its own text content (`_FOLLOWERS_TEXT_RE`, an anchored `[\d,]+ followers?` pattern), not by a link or CSS class. LinkedIn used to render this as an anchor to `/people-follow/followers`; it is now plain, non-interactive text (`<p>2,614 followers</p>`) with build-hashed classes that reshuffle every deploy, so text content is the only thing left stable enough to match on — confirmed live via `--debug-followers` on the `__main__` probe below, which dumps HTML context around every "follow" occurrence on the page when the match misses. The same count is duplicated verbatim elsewhere on the page (near the Activity section); `.first` picks the top-card occurrence, though either resolves to the same number. It deliberately does **not** call `actions/search.py:visit_profile()` for that navigation: `visit_profile()`'s side effect of discovering and enriching every other profile linked from the page is a paced, potentially multi-profile Voyager crawl, and `collect_dossier` runs under `pipeline/locks.py:campaign_lock` — running that crawl here would hold the campaign-wide lock for it on every expensive-stage qualification, serialising every other account behind one lead's follower-count lookup. `_goto_profile_page()` is a private, discovery-free navigation instead. Same fail-soft contract as the rest of the module: missing text, unparsable text, or a navigation error all return `None`.

**Cost.** One expensive qualification is `1 + 1 + 1 + 2×(current companies)` LinkedIn reads — typically 5-7, where the old flow was 1. One of those — follower count — is a full page navigation rather than a fetch, so it's the priciest of the list in wall-clock time. They are spaced by `CAMPAIGN_CONFIG["dossier_{min,max}_delay_seconds"]` (2-4s jittered), and `dossier_posts_per_source` (3) caps the post fetches. This request amplification is the entire reason the cheap prefilter short-circuits *before* the dossier is collected rather than merely before the expensive LLM call — a lead the cheap stage rejects costs zero LinkedIn reads at qualify time.

- **`llm.py`** — `get_llm_model(role)` factory + `run_agent_sync(coro)` sync boundary. `role` is `"expensive"` (general-purpose, higher-end model — `agents/follow_up.py`, search-keyword generation, fact extraction/reconcile, and the expensive qualification stage) or `"cheap"` (fast/cheap, used only by the disqualify-only qualification prefilter) — see "Qualification Pipeline" above. `get_llm_model(role)` reads the `{role}_*` fields off `SiteConfig` and dispatches via per-provider builders (OpenAI / Anthropic / Google / Groq / Mistral / Cohere / openai_compatible) to the right `pydantic_ai.models.Model` — each role can use a different provider entirely. The `openai` builder uses `OpenAIResponsesModel` (Responses API), not `OpenAIModel`/`OpenAIChatModel` (Chat Completions) — OpenAI's Chat Completions endpoint rejects structured output (function tools, which every `Agent(..., output_type=...)` call site here uses) combined with `reasoning_effort` for reasoning-capable models (o-series, GPT-5.1+): `400 invalid_request_error` telling you to use `/v1/responses` instead. `openai_compatible` stays on `OpenAIModel`/Chat Completions since arbitrary compatible endpoints only implement that surface. Call sites build `Agent(get_llm_model(role), ...)` and invoke `run_agent_sync(agent.run(prompt))` — never `Agent.run_sync`, whose anyio portal leaves the caller's thread running-loop slot populated and poisons subsequent sync Playwright calls (`"using Playwright Sync API inside the asyncio loop"`). `run_agent_sync` drives the coroutine to completion on a short-lived worker thread with its own event loop; per-thread asyncio slots are independent, so the caller's thread stays clean regardless of what anyio / pytest-anyio / Jupyter / etc. did to it.
- **`tracing.py`** — Optional LLM call tracing to an Arize Phoenix server. `setup_tracing()` is off by default (no `phoenix`/`opentelemetry` import at all) unless `PHOENIX_COLLECTOR_ENDPOINT` is set, in which case it calls `phoenix.otel.register(endpoint=..., project_name=PHOENIX_PROJECT_NAME or "openoutreach", protocol="http/protobuf", auto_instrument=False)` then `pydantic_ai.Agent.instrument_all(True)`. `instrument_all` sets pydantic-ai's process-wide default, so every `Agent(...)` call site in `linkedin/` is traced automatically without passing `instrument=` at each one — the follow-up agent, both qualification-cascade stages, search-keyword generator, and both fact-extraction/reconciliation calls in `db/summaries.py`, across both LLM roles. `auto_instrument=False` deliberately skips wiring up any other installed OpenInference instrumentors (e.g. a raw openai/anthropic one), since pydantic-ai's own instrumentation already captures the full request/response at the model-call boundary — double-instrumenting would double-trace the same HTTP call. **Endpoint normalization is manual and deliberate**: `phoenix.otel.register()` only appends the OTLP HTTP collector path (`/v1/traces`) when its own `endpoint` argument is left `None` and it re-reads `PHOENIX_COLLECTOR_ENDPOINT` itself; passing the value through explicitly — required here so tracing stays gated on our own presence check rather than `register()`'s own env lookup — skips that normalization entirely. An endpoint like `http://host:6006` would then be POSTed to verbatim, landing on Phoenix's UI route instead of its collector route and failing with `405 Method Not Allowed` (reproduced against a stub HTTP server during development — the exporter doesn't retry onto a different path, it just logs the failure and drops the batch). `setup_tracing()` strips a trailing slash and appends `/v1/traces` itself if not already present, and pins `protocol="http/protobuf"` unconditionally rather than relying on `register()`'s own port/path sniffing (which infers gRPC from port `4317` and otherwise falls back to HTTP with a warning) — the project's Docker setup only ever publishes an HTTP collector port, so there's no ambiguity to infer. Called once at process start, right after `configure_logging`, from both `rundaemon.Command.handle` and `browser/registry.py:cli_parser` (every CLI debug script goes through the latter), so tracing covers the daemon and manual one-off runs alike. No Phoenix server is bundled — point `PHOENIX_COLLECTOR_ENDPOINT` at one you run yourself (e.g. `http://localhost:6006`).
- **`exceptions.py`** — `AuthenticationError`, `TerminalStateError`, `SkipProfile`, `PageStructureError`, `ReachedConnectionLimit`, `ConnectClickFailed`, `ProfileInaccessibleError`. `SkipProfile` vs `PageStructureError` is the load-bearing distinction: the first is a verdict on the *lead* (404, gone) and callers close the Deal FAILED; the second is a verdict on the *page render* and callers must never close the Deal — see "Top card lookup" below.

### Top card lookup (`browser/nav.py:find_top_card`)

Every connect/status decision is scoped to the profile's top card, found by trying `TOP_CARD_SELECTORS` in priority order. Three properties matter, all learned from the same failure mode — one account logging `Top card not found` on every profile while another account, same code, same container, sails through:

**It waits.** Profiles are navigated with `wait_until="domcontentloaded"`, which fires before LinkedIn's SPA has rendered anything. The lookup used to be a bare `count()` snapshot with no wait at all, so whichever account's page hydrated slower simply lost the race. It now waits up to `TOP_CARD_TIMEOUT_MS` (15s) for *any* known variant to attach, then re-scans in priority order — the wait is a comma-joined locator, which resolves in DOM order, so it can only be used to know *when* to look, not *what* to pick.

**The SDUI selector is element-agnostic and suffix-anchored.** `[componentkey$="Topcard"]`. Both properties were paid for in production. The list used to be entirely `section`-prefixed, including its SDUI entry (`section[componentkey*="com.linkedin.sdui.profile.card"]`) — but LinkedIn's current profile render puts that key on a **`<div>`**, so on an account that had the rollout *every* selector missed and the account failed every profile while its neighbour, on identical code, sailed through. That page also has no `<h1>` and only 10 `<section>` elements, none of them the top card, so structural fallbacks anchored on the document outline don't rescue it either. And the suffix matters as much as the element: `com.linkedin.sdui.profile.card.ref<profileId>` prefixes *every* card on the page — About, Featured, Services, SuggestedForYou, 8 in all — so matching the prefix and taking `.first` scopes the connect lookup to whatever card sorts first in the DOM. Only the `Topcard` suffix is unique.

**Scoping to the top card is a safety property, not a performance one.** A profile page carries other members' connect buttons in its "More profiles for you" rail. On the captured page the *only* page-wide match for `invite_to_connect` belonged to an unrelated sidebar suggestion, while the target's own button was `_pending` inside the top card — so a lookup that widened its scope on a miss would send an invitation to the wrong person. That rules out "fall back to searching `main`" as a recovery strategy: failing closed is correct here.

**Prefer the SDUI componentkey over `aria-label` for button state.** The connect button renders as `componentkey="ConnectButtonstate:invitation:urn:li:member:<id>_pending"` (or `_connect`). The state is in the key, so `[componentkey^="ConnectButton"][componentkey$="_pending"]` reads it structurally, where the older `[aria-label*="Pending"]` only works while the account renders LinkedIn in English. Both are kept, componentkey first.

**A miss is self-diagnosing and never terminal.** The three things a miss can mean — LinkedIn served this member a different markup variant (its profile rewrite rolls out per-member, so it genuinely hits one account and not another), the session is being throttled behind an interstitial that keeps the `/in/<slug>/` URL, or the page just hadn't rendered — are indistinguishable from a log line saying "not found", and the browser has moved on by the time anyone reads it. So `find_top_card` logs a fingerprint (page title, HTML size, and which of `_MISS_MARKERS` — auth wall, challenge, unavailable, rate limited, legacy/SDUI markup present — appear in the HTML) and dumps the unmatched page to `tests/fixtures/pages/top-card-miss/{account}_{slug}_{ts}.html`. That dump is deliberately **not** gated behind `DUMP_PAGES`, which is for bulk fixture collection; this fires only on an otherwise-undiagnosable failure. `python -m linkedin.browser.nav --file <dump>` replays those selectors against a saved dump offline (no session needed) and prints which one should have fired, what the buttons scope to, and the page-wide connect match for comparison; `--profile <public_id>` does the same against a live page. It then raises `PageStructureError`, and both handlers treat it as inconclusive rather than fatal: `tasks/check_pending.py` stays PENDING and doubles the backoff (the invite is still live on LinkedIn regardless of what the DOM said, and FAILED is terminal — it is where LLM rejections live), `tasks/connect.py` leaves the deal READY_TO_CONNECT without touching `connect_attempts`, whose give-up path calls `disqualify_lead()` and excludes the Lead campaign-wide. Both self-heal the moment profile pages render again.

## Admin panel (`webadmin/`)

FastAPI app, a separate process from Django (`uvicorn webadmin.main:app`), serving the same `/admin/` path Django Admin used to. Replaces `admin.py` + `crm/admin.py` + `linkedin/dashboard.py` + `templates/admin/index.html` + `django-unfold` in one pass — Django keeps owning models/migrations; this only replaces who serves the CRUD/dashboard HTTP layer.

- **Multi-account note** — `Deal.assigned_profile` and `Task.linkedin_profile` are shown as columns and filters so you can see which LinkedIn account owns each lead and each queued action; `Campaign.assignment_cursor` mirrors the rotation pointer. `LinkedInProfile.user` renders as a dropdown (not a raw id) because adding a second account to a campaign means picking the user that campaign already belongs to, and there is no user admin to look ids up in. `LinkedInProfile.__str__` deliberately does not touch `self.user` — these objects are loaded without relationships for FK columns, and a lazy load there raises `MissingGreenlet` under the async session.
- **Data layer** (`webadmin/models.py`) — async SQLAlchemy (`asyncpg`) models mirroring the exact tables Django's migrations already created (`crm_lead`, `crm_deal`, `linkedin_campaign`, `linkedin_campaign_users`, `linkedin_linkedinprofile`, `linkedin_searchkeyword`, `linkedin_actionlog`, `linkedin_task`, `linkedin_siteconfig`, `chat_chatmessage`, `auth_user`). This is a deliberate tradeoff (user's explicit choice over reusing the Django ORM directly): Django remains the only thing that alters schema, but this column set must be hand-kept in sync with `crm/models/`, `linkedin/models.py`, `chat/models.py` whenever a future migration changes one of these tables. `webadmin/config.py` builds its own async Postgres DSN from the same `DATABASE_URL` Django resolves, via the shared `db_url.py` helper (`sqlalchemy_async_url()`) — no Django import needed for DB connectivity. `ChatMessage.content_type_id`/`object_id` (Django `GenericForeignKey`) isn't resolved generically — confirmed via grep that `content_object` only ever targets `Lead` in this codebase, so `object_id` is treated as a `crm_lead` id directly.
- **Admin engine** (`webadmin/registry.py`, `webadmin/views.py`) — `ModelAdmin`/`AdminAction` dataclasses (list_display/list_filter/search_fields/date_hierarchy/readonly_fields/raw_id_fields/m2m_fields/choices/actions/can_add/can_delete/hidden_from_nav), one instance per model in `webadmin/admins.py` — the direct analog of the old `ModelAdmin` subclasses in `admin.py`/`crm/admin.py`. `views.py:build_router(admin)` generates the full list/add/edit/delete/action route set generically from a `ModelAdmin` + SQLAlchemy column introspection (`build_field_specs`) — form fields are typed from the column (text/textarea/number/float/checkbox/datetime/json/binary/select/fk/m2m), FK fields render as either a raw-id number input or a `<select>` per `raw_id_fields`, choice fields render as a `<select>` from a plain Python `Enum` hand-mirrored from the Django `TextChoices` in `admins.py`. Every model gets a built-in "Delete selected" bulk action plus whatever custom `AdminAction`s it declares.
- **Ported behavior** (`webadmin/admins.py`) — `SiteConfigAdmin` (`can_add=False`, `can_delete=False`) is a singleton shown in the nav as "Site Configuration"; its one-row list links to `/admin/siteconfig/1/edit`, where the LLM keys are set (Add/Delete suppressed since there is only ever one row). `TaskAdmin.run_now` (jump PENDING tasks to `scheduled_at=now()`, warns on skipped non-pending selections), `LeadAdmin.mark_human_takeover`/`resume_ai` are ported verbatim from the old `run_now`/`mark_human_takeover`/`resume_ai` actions. Deviation: `Task`, `ActionLog`, and `ChatMessage` drop the Add button entirely (`can_add=False`) — in the old admin every field on these was already `readonly_fields`, so the Add form was already unusable; this just removes the dead affordance.
- **Auth/session/CSRF** (`webadmin/auth.py`, `webadmin/csrf.py`) — login checks the existing `auth_user` table (same rows `DJANGO_SUPERUSER_*`/`createsuperuser` populate) via `django.contrib.auth.hashers.check_password` — a pure function, so `webadmin` does a settings-only `django.setup()` at startup for this one purpose, never for ORM queries. Session is a signed cookie (Starlette `SessionMiddleware`, keyed off `DJANGO_SECRET_KEY` — no new secret to manage). CSRF is a hand-rolled double-submit cookie (`CSRFCookieMiddleware` sets `webadmin_csrf`; every POST must echo it in a `csrf_token` field) since Django's `CsrfViewMiddleware` no longer runs anywhere.
- **`webadmin/dashboard.py`** — home route. Global stat tiles: the original 4 (messages sent, replies received, connect requests sent/accepted, ported from `linkedin/dashboard.py` + `templates/admin/index.html`) plus 3 more — profiles scanned (`crm_lead` row count), leads messaged, leads replied (both `COUNT(DISTINCT ChatMessage.object_id)`, split on `is_outgoing`) — plus 2 qualification-funnel tiles, "Disqualified — Cheap Stage" and "Reached Expensive Stage" (`_qualification_funnel_stats()`, a flat `COUNT` per `Deal.qualification_stage` value — see "Qualification Pipeline" above). Below the tiles, a "Metrics by Profile" table breaks the messaging/connect counts down per `LinkedInProfile` (account) — deliberately *not* the funnel tiles, since qualification runs against the campaign-wide pool before any account owns the lead (`Deal.assigned_profile` is null on every disqualified or freshly-QUALIFIED Deal), so there's no single account to attribute a qualification decision to. `ChatMessage` carries no `linkedin_profile` FK — only the `Lead` it's about (`object_id`) — so `_per_profile_stats` recovers the owning account by joining `ChatMessage.object_id == Deal.lead_id` and grouping on `Deal.assigned_profile_id`; this relies on the "ownership is sticky" invariant (see Multi-account campaigns above) that a lead's conversation only ever lives on the account its Deal is assigned to. Connect-request counts join `ActionLog.linkedin_profile_id` (sent) and `Deal.assigned_profile_id` + state (accepted) the same way the global tiles do, just grouped instead of aggregated flat.

  A third table, "Daily Metrics", buckets the last `DAILY_WINDOW_DAYS` (14) UTC calendar days via `func.date(...)` on each event's own timestamp column (`ChatMessage.creation_date`, `Lead.creation_date`, `ActionLog.created_at`, `Deal.creation_date`), newest first, backfilling missing days with zeros in Python rather than a DB-side `generate_series` — keeps the query portable and the gap-filling logic readable. A `<select name="profile_id">` above the table (plain `GET` query param, `onchange="this.form.submit()"` — no JS framework in this template) switches `_daily_stats(session, profile_id=...)` between two shapes: with no profile selected (`profile_id=None`) it's the full 9-column accumulated view — day, profiles scanned, leads messaged/replied, messages sent, replies received, connect requests sent, and the two funnel columns (`cheap_disqualified`/`reached_expensive`, day-bucketed the same way as the global tiles); with a profile selected, the messaging/connect columns are re-run joined to `Deal.assigned_profile_id == profile_id` (same join `_per_profile_stats` uses) and the "profiles scanned"/funnel columns are dropped entirely — same non-attributability reasoning as the lifetime per-profile table above, not just zeroed out, since zeros there would misleadingly read as "this account scanned nothing" rather than "this isn't a per-account event." Connect-request *accepted* is deliberately left out of the daily table in both shapes: `ActionLog` never logs an "accepted" event (only `connect`/`follow_up` sends), and `Deal.update_date` is bumped by any later write to the row (chat_summary, fit_score, …), so it can't stand in for "the day the invite was accepted" — the lifetime total stays on the global/per-profile tiles only.

## Docker

`BUILD_ENV` arg selects requirements. Dockerfile at `compose/linkedin/Dockerfile` (two-stage: deps build → runtime; installs Playwright chromium + a VNC stack: Xvfb, x11vnc, websockify, noVNC). One container exposes three ports: **8000** (FastAPI admin panel, always up), **6080** (noVNC in-browser browser view), **5900** (native VNC client). `local.yml` publishes all three and auto-creates a superuser via `DJANGO_SUPERUSER_*` env. See `compose/linkedin/start` for the process supervision.

Both `docker-compose.yml` and `local.yml` also define a `db` service (`postgres:16-alpine`, data in the `openoutreach_pgdata` named volume) with a `pg_isready` healthcheck; `app` declares `depends_on: db: condition: service_healthy`, so `start`'s `migrate --no-input` only runs once Postgres is actually accepting connections — no wait-loop needed in the start script itself.
