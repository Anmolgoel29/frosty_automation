# CLAUDE.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Dependencies**: Managed in `requirements/*.txt` (used by local dev and Docker).
- **Docs sync**: When modifying code, update CLAUDE.md and ARCHITECTURE.md to reflect changes.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in CLAUDE.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **No API backward compat**: Project has no external users yet — don't preserve old Python APIs, function signatures, or import paths. Rename, delete, and rewrite freely; no shims or re-export modules. DB schema changes still go through Django migrations as normal — existing installs must upgrade cleanly.
- **No Docker**: Never run `docker` commands directly. If a task needs Docker (e.g. spinning up Postgres for testing), give the exact command(s) to the user and ask them to run it and paste back the output.
- **Production data is real**: The databases hold actual users' valuable data. Migrations and schema changes must be non-destructive and preserve existing data — no dropping/truncating tables or columns that hold data without an explicit, reviewed data-migration path; no changes that could silently lose or corrupt rows on an existing install.

## Project Overview

OpenOutreach — self-hosted LinkedIn automation for B2B lead generation. Playwright + stealth for browser automation, LinkedIn Voyager API for profile data, Django ORM + migrations for the CRM data model (models owned by this project), FastAPI (`webadmin/`) for the admin web UI.

```bash
# Local dev

# Testing
make test / make docker-test

```

## Architecture (quick reference)

For detailed module docs, see `ARCHITECTURE.md`.

- **Entry**: `manage.py` — stock Django management. `rundaemon` command (migrate → onboard → validate → build one AccountSession per active LinkedIn account → task queue loop). `manage.py` with no args defaults to `rundaemon`. Onboarding logic in `onboarding.py`: `OnboardConfig` (pure dataclass), `missing_keys()`, `collect_from_wizard()` (non-interactive — loads `config.json` from data dir / cwd / `~/.openoutreach/`, else defaults), single `apply()` write path. `_ensure_onboarded()` applies whatever config it finds; if required fields are still missing it exits (the Docker supervisor retries once you finish onboarding via the admin panel or `config.json`). Docker `start` script runs Xvfb/VNC + the FastAPI admin web server (`uvicorn webadmin.main:app --port 8000`, always up) + a supervised `rundaemon` loop, all in one container.
- **Multi-account campaigns**: a campaign runs on every active `LinkedInProfile` whose Django user is in `Campaign.users` (`Campaign.active_profiles()`, ordered by pk). `LinkedInProfile.user` is a plain FK, not one-to-one — several LinkedIn accounts can share one Django user and thereby its campaign membership (that's the easy way to add a second account in the admin: LinkedIn Profile → Add → pick the user the campaign already belongs to). Everything upstream of the connect step is **shared**: search, enrichment and qualification write into one campaign-wide Lead/Deal pool, driven by whichever account's connect task is running. The pool is divided exactly once, at the connect step: `linkedin/pipeline/allocation.py:allocate_ready_deals(campaign)` hands each un-owned READY_TO_CONNECT Deal to one account in rotation (`Campaign.assignment_cursor` is the persisted pointer) and stamps `Deal.assigned_profile`. Ownership is then **sticky and never crosses over** — only the owning account connects, polls the invite, and runs the conversation, because the pending invite and the message thread only exist on the account that sent them. `get_ready_to_connect_profiles()` is account-scoped; `get_qualified_profiles()` is not. `set_profile_state()` claims an un-owned deal for the acting account when it enters PENDING/CONNECTED (covers seeded leads that never pass through allocation). `reclaim_unreachable_deals()` returns *un-contacted* leads held by a deactivated/detached account to the pool; contacted ones are deliberately left stranded with a warning. Each account has its own rate limits (`can_execute`) and its own browser, so one account hitting its daily cap doesn't stall the others. Accounts run in parallel, one worker thread each (see Parallel execution). `daemon.sync_sessions()` re-reads the account roster on every idle cycle, so an account added or deactivated in the admin joins/leaves within ~a minute without a restart. Add accounts with `manage.py add_profile --email … --password … [--campaign NAME] [--user existing_handle]` (`--list` shows the accounts per campaign), via the admin panel, or via `additional_accounts` in `config.json`.
- **Parallel execution**: one worker thread per LinkedIn account (`daemon._AccountWorker`), each with its own browser — the accounts search and connect *at the same time* instead of taking turns. The Playwright sync API is thread-affine, so a session's browser is only ever created, driven, and closed by its own worker; the supervisor asks a worker to stop rather than closing anything itself. The main thread is the supervisor: it re-reads the account roster (`sync_sessions`), respawns dead workers, and is the **single writer for `reconcile()`** (workers only enqueue their own follow-on tasks). Concurrency safety rests on: `Task.objects.claim_for(profile_id)` (`SELECT … FOR UPDATE SKIP LOCKED` + mark RUNNING in one transaction; among an account's own due tasks it orders by priority — `follow_up` and `check_pending` tied first, `connect` last — before falling back to `scheduled_at`, so a worker sends a due message or polls a pending invite before it spends time hunting for a new candidate), `scheduler._TASK_LOCK` (makes check-then-insert dedup atomic — without it two threads create duplicate follow_ups and the lead gets messaged twice), `pipeline/locks.py:campaign_lock(campaign)` (serialises `run_qualification`/`promote_to_ready`/keyword generation — one shared unlabelled pool per campaign; without it two accounts could pick the same lead and double-spend LLM calls), `search._claim_keyword` (`SKIP LOCKED`, so accounts take *different* keywords — this is how search work is divided), and `IntegrityError` tolerance in `create_enriched_lead`/`Lead.get_profile` (two accounts routinely discover the same person). `recover_stale_running_tasks()` is **startup-only** — RUNNING now means "a worker is executing this", so resetting those mid-run would double-execute live work; reconcile skips live tasks via `has_live_task()` (PENDING *or* RUNNING). `daemon._StartSpacer` holds a jittered `account_stagger_{min,max}_seconds` gap between task *starts* so two accounts on one IP don't fire their first request in the same instant (tasks still overlap — that's the point). Log lines are tagged with the worker's thread name (the account) via `ColoredFormatter`.
- **Per-account browser view (VNC)**: each account renders on its own Xvfb display, `:100 + profile_id` (`vnc.py:display_for`, spawned on demand by `session.ensure_display()` → `_ensure_xvfb`, gated on `OPENOUTREACH_PER_ACCOUNT_DISPLAY` which `compose/linkedin/start` sets — off by default so local dev uses the real X server). **One** VNC server serves all of them on the existing 6080/5900: `compose/linkedin/start:vnc_follow_selected_display` polls `vnc.py:DISPLAY_CONTROL_FILE` and restarts x11vnc against whichever display it names (tracked by pid, not `pkill` — procps isn't guaranteed in the base image). With nothing selected it defaults to the **lowest live per-account display**, not `:99` — `:99` is a bare desktop with no browser on it. Switch accounts via Admin → LinkedIn Profile → tick one → "Watch this account's browser (VNC)" (`webadmin/admins.py:_watch_browser`), then reload the noVNC tab (`?reconnect=1` reconnects on its own). A per-account VNC *port* was rejected: ports must be published before the container starts, which would rule out adding accounts to a running daemon. `/start` is baked into the image, not under the `/app` bind mount — **changing it needs `make build`**. `_ensure_xvfb`'s liveness check verifies the lock file's PID is actually alive rather than trusting the file's mere existence — a container SIGKILLed (OOM, stop timeout) and restarted without recreation leaves a stale lock behind (Xvfb never got to clean it up), which otherwise silently skips starting a real Xvfb and cascades into `XOpenDisplay failed` / `Missing X server or $DISPLAY`. `launch_browser` (`browser/login.py`) calls `playwright.stop()` on any failure after `.start()` before re-raising — a leaked Playwright connection (its sync-API dispatcher runs on a greenlet on the *calling* OS thread) otherwise poisons that thread's asyncio "running loop" state permanently, breaking every later browser launch on that account's worker thread with an unrelated `"using Playwright Sync API inside the asyncio loop"` error until the whole daemon restarts.
- **State machine**: `enums.py:ProfileState` — QUALIFIED → READY_TO_CONNECT → PENDING → CONNECTED → COMPLETED / FAILED. Deal.state is a CharField with ProfileState choices (no Stage model). `Outcome` (converted/not_interested/wrong_fit/no_budget/has_solution/bad_timing/unresponsive/unknown) on Deal.outcome. `Lead.disqualified=True` = permanent exclusion. LLM rejections = FAILED Deals with wrong_fit outcome (campaign-scoped).
- **Task queue**: `Task` model (persistent). Three types: `connect`, `check_pending`, `follow_up`. Every Task carries `linkedin_profile` — the account that must execute it — and the daemon routes it to that account's browser session (a task whose account isn't running is failed, never re-homed). Handlers in `linkedin/tasks/`, signature: `handle_*(task, session)`. Task creation is centralized in `linkedin/tasks/scheduler.py` — no other module inserts Task rows; every `enqueue_*` takes the executing profile and dedups on it. `set_profile_state()` fires `on_deal_state_entered(deal)`, which enqueues the task implied by the new state (CONNECTED → follow_up, PENDING → check_pending) against `deal.assigned_profile`. The CONNECTED → follow_up enqueue uses `delay_seconds=0` (not the generic 10s default), so the moment a `connect` or `check_pending` task observes an accepted invite, the first message goes out on the account's very next claim rather than waiting out a delay. The daemon calls `reconcile(sessions)` whenever the queue has no ready task: it recovers stale RUNNING rows, reclaims/allocates ready leads, seeds one connect per (campaign, account), and re-creates tasks for any active Deal without a pending task. This is the retry mechanism — a crashed handler leaves a FAILED task with no successor, and the next idle cycle re-creates it. On 401 (`AuthenticationError`), the daemon calls `session.reauthenticate()` and marks the task FAILED; reconcile picks it up. The idle wait loop polls every `QUEUE_POLL_INTERVAL` (60s) instead of sleeping the full delay in one block, so the Task admin's "Run now" bulk action (sets `scheduled_at = timezone.now()` on selected PENDING tasks) takes effect within ~60s — e.g. to make the AI answer a fresh reply immediately instead of waiting out a `follow_up` task's scheduled backoff. `handle_follow_up` syncs the conversation (`db/chat.py:sync_conversation`) before its `_too_soon_to_nudge`/`_unanswered_count` cooldown gates run (not after, as `run_follow_up_agent` used to do it) — those gates read local `ChatMessage` rows, so gating pre-sync would judge a reply that already arrived on LinkedIn by stale local state and just re-enqueue without ever seeing it, defeating "Run now" too.
- **DB query budgets**: the daemon loops forever, so hot paths must cost a *constant* number of queries, not one per row. Enforced by `tests/test_db_query_budget.py` (asserts cost is flat as the pipeline grows). The rules that came out of measuring it: `reconcile()` reads the live queue once per campaign into `_live_task_keys()` and `bulk_create`s everything missing (was 2 queries per active deal, every 60s — 163 queries at 50 deals, now 11 and flat); `fetch_next_qualification_candidate()` is a single-row query (plain FIFO — see ML pipeline below) and `has_qualification_candidates()` is the cheap EXISTS for callers that only need yes/no; `promote_to_ready()` is one bulk `UPDATE ... WHERE fit_score >= threshold`, not a loop; `get_ready_to_connect_profiles()` orders by `fit_score` at the DB level, so ranking the ready pool costs the same one query regardless of pool size; `set_profile_state()` saves with `update_fields` so it never rewrites `profile_summary`/`chat_summary`; `allocate_ready_deals()` does one UPDATE per account, not per lead; `_sync_from_api()` bulk-creates after one existence query (LinkedIn messages are immutable, so existing rows are skipped, not upserted); `AccountSession._maybe_refresh_cookies()` re-reads the cookie blob at most once per `COOKIE_CHECK_INTERVAL` (300s) instead of on every `ensure_browser()`. Deliberate exception: `can_execute()` keeps its `refresh_from_db` so an admin limit change takes effect on the next check — it runs once per task, not in a loop.
- **ML pipeline (qualification)**: a two-stage LLM cascade — no statistical model, no active learning. `pipeline/qualify.py:run_qualification()` pulls the oldest un-dealt Lead in the campaign (plain FIFO) and runs it through `ml/qualifier.py:qualify_cheap()`, a fast/cheap LLM call scoped to `role="cheap"` that only ever *disqualifies* — it sees exactly two fields, `Lead.headline` and `Lead.about`, both cached at discovery time in `db/leads.py:create_enriched_lead` from the profile dict already in hand (no extra scrape, no network at all at qualify time), and is prompted to reject only when it's highly confident the profile is an obvious mismatch; anything it doesn't confidently reject passes through untouched. **Legacy-row repair**: those two columns were added after the GP→LLM switch, so leads discovered before it — and url-only seeds (`setup/seeds.py`, `setup/freemium.py`) — carry the blank column default and can never be judged; the prompt passes every blank lead through, so the cheap stage silently degrades to a no-op that still costs an LLM call. `Lead.coarse_scraped_at` (null = "coarse fields never came from a real scrape") drives the fix: `db/leads.py:ensure_coarse_fields(session, lead)` runs just before `qualify_cheap` and gives any un-repaired row exactly one profile re-scrape, stamping the marker so it never repeats — including when the profile legitimately has no About section. Rows that already hold coarse data are stamped without a scrape; an unreachable profile leaves the marker null and falls through to the dossier stage, which disqualifies it on the same unreachable profile a moment later. So the cheap stage is network-free in steady state, and the repair cost drains away with the legacy backlog. Clearing `coarse_scraped_at` in the admin forces a re-scrape of that lead. Whatever survives goes to `qualify_with_llm()`, scoped to `role="expensive"`, which reads the **full dossier** (`ml/dossier.py`, see below) and makes the real qualify/reject call plus a 1-5 `fit_score` self-rating, stored on `Deal.fit_score`. `fit_score` replaces the old GP posterior for the two things it used to drive: `pipeline/ready_pool.py:promote_to_ready(session, threshold)` bulk-promotes QUALIFIED deals with `fit_score >= threshold` (config: `CAMPAIGN_CONFIG["min_fit_score"]`) to READY_TO_CONNECT, re-evaluating the whole backlog on every call — so tightening or loosening the bar mid-campaign takes effect on leads already sitting QUALIFIED, not just future labels; `get_ready_to_connect_profiles()` orders by `fit_score` descending, so the strongest-rated leads in an account's allocated pool get contacted first, with no separate ranking pass. The point of dropping the GP: a model refit on *all* accumulated history has no way to "forget" labels from before a campaign objective changed, so a mid-campaign pivot fights stale geometry until new labels statistically dominate; a pure LLM cascade has no such memory — a `product_docs`/`campaign_objective` edit takes effect on the very next lead. `qualify_source`/`ready_source` (`pipeline/pools.py`) lost their exploit/explore acquisition-strategy branching along with it — search is triggered purely by "the backlog is empty" (`has_qualification_candidates`), nothing more. `linkedin/ml/qualifier.py` also still hosts `KitQualifier` (unrelated — pre-trained GPR kits for freemium campaigns, currently unreachable since freemium kit import is disabled) and the GP numerics (`_gpr_predict`, `_prob_above_half`, `_rank_by_score`, `_load_profile_embeddings`) it depends on.
- **Qualification dossier (`ml/dossier.py`)**: what the *expensive* stage reads. `collect_dossier(session, lead)` gathers the profile (`Lead.get_profile` — headline, full About, complete experience + education), the lead's follower count, the lead's 3 most recent posts, and then for **every company the lead currently works at** (a position with no `date_range.end`, deduped on the company page slug — a lead active at three companies gets all three scraped) that company's page (About, industry, employee count, follower count, tagline) plus its 3 most recent posts. `render_dossier()` turns it into **explicitly labelled** plain text (`Company industry: Software Development`, `Currently active in this role: yes`) — every value names the field it came from so the model never has to infer what a bare line is; missing values render as `unknown`/`(empty)`/`none found` and the prompt tells the model to read those as missing, not as negative signals. **Nothing is truncated** — the expensive stage sees whole About sections, whole role descriptions and full post bodies. The extra reads live in `api/enrichment.py` (`fetch_member_posts`, `fetch_company`, `fetch_company_posts` — Voyager; `fetch_follower_count` — a DOM scrape, see below), which is **fail-soft by design**: every one returns `None`/`[]` rather than raising, so a private company page, a moved endpoint, or a changed selector degrades the dossier instead of killing qualification for an otherwise good lead — only `AuthenticationError` propagates (the daemon re-authenticates on 401). Those Voyager endpoints are LinkedIn-internal and unversioned; `python -m linkedin.api.enrichment --profile <public_id> --company <slug>` probes them (and the follower-count scrape) against a live session when one starts coming back empty. `fetch_follower_count` is the odd one out: LinkedIn retired the old `networkinfo` Voyager endpoint it used to read (HTTP 410) and never put the field on the main profile decoration either, so it now navigates to the profile page and reads the top card's "X followers" text, matched by its own text content (`_FOLLOWERS_TEXT_RE`) rather than by a link or CSS class — LinkedIn used to render this as an anchor to `/people-follow/followers`, but it is now plain, non-interactive text, and the classes around it are build-hashed and reshuffle every deploy. `--debug-followers` on the `__main__` probe (auto-fires on a miss) dumps HTML context around every "follow" occurrence on the page for diagnosing the next drift. That navigation deliberately goes through a private `_goto_profile_page()` rather than `actions/search.py:visit_profile()`, to avoid `visit_profile`'s discover-and-enrich side effect (a paced, potentially multi-profile Voyager crawl) running while `collect_dossier` holds `pipeline/locks.py:campaign_lock` — that would stall every other account in the campaign behind one lead's follower-count lookup. Every CLI debug script (including `python -m linkedin.ml.dossier --profile <public_id>`, which runs the full dossier scrape and prints it) takes `--headless` via the shared `cli_parser()`/`cli_session()` helper, for environments without a display/VNC set up — the daemon's real accounts are unaffected and always launch headed. **Cost**: one expensive qualification is now `1 profile + 1 follower count + 1 posts + 2 per current company` LinkedIn reads where it used to be 1 — the follower count is a full page navigation rather than a fetch, so it's the priciest of that list in wall-clock time — spaced by `CAMPAIGN_CONFIG["dossier_{min,max}_delay_seconds"]` (2-4s) — which is exactly why the cheap stage short-circuits *before* the dossier scrape, not just before the expensive LLM call.
- **LLM tracing**: `linkedin/tracing.py:setup_tracing()`, off by default — set `PHOENIX_COLLECTOR_ENDPOINT` (e.g. `http://localhost:6006`, Phoenix's default HTTP port) to export every LLM call to an Arize Phoenix server (`PHOENIX_PROJECT_NAME` optional, defaults `openoutreach`). The `/v1/traces` collector path is appended automatically if the endpoint doesn't already end with it, and the exporter is pinned to `protocol="http/protobuf"` — passing `endpoint=` explicitly to `phoenix.otel.register()` (needed to gate tracing on our own presence check) bypasses its env-var auto-normalization, so an un-suffixed endpoint silently POSTs to the server's UI root and fails with `405 Method Not Allowed` instead of exporting; ARCHITECTURE.md has the full story. Uses pydantic-ai's built-in OpenTelemetry instrumentation (`Agent.instrument_all(True)`), a process-wide default every `Agent(...)` call site picks up automatically — no per-call-site changes needed. Called once at process start (right after `configure_logging`) from `rundaemon.Command.handle` and `browser/registry.py:cli_parser`, so both the daemon and manual CLI debug scripts are covered. No Phoenix server is bundled; run your own and point the env var at it. Two levels of span, both no-ops when tracing is off: `task_span()` (one per daemon Task, opened by `daemon.py:_run_task`) and, nested inside it, `agent_run()`/`finish_agent_run()` — one span per individual LLM decision, kind `AGENT` so it renders distinctly in Phoenix from the `LLM`-kind span pydantic-ai nests under it. This matters because a single Task can drive more than one decision — a `connect` task's `qualify_source` loop can run the cheap *and* expensive qualifier over several candidate leads before landing one that promotes — so without per-decision spans those calls are indistinguishable anonymous leaves under one Task trace. `pipeline/qualify.py` wraps both cascade stages this way: the span carries the model identity (`model.model_id`, read off the built `pydantic_ai.Model` — no extra query), the lead, the campaign, and the decision + reasoning as the span's output/metadata, so which LLM qualified or disqualified a given lead, and why, is directly visible and filterable per-trace in Phoenix rather than something to reconstruct from the CRM database. The same fields go to the process log at INFO either way.
- **Remote kits**: Freemium campaign kit download/import is disabled; the daemon only uses locally configured campaigns.
- **Newsletter**: Auto-subscription is disabled for self-hosted runs; no outbound newsletter signup requests are made.
- **Config**: `SiteConfig` DB singleton — two fully independent LLM configs: `expensive_*` (general-purpose, higher-end model — follow-up messaging agent, search-keyword generation, fact extraction/reconcile, and the real qualify/reject + fit-score call) and `cheap_*` (fast/cheap, used in exactly one place: the disqualify-only qualification prefilter) — see ML pipeline above. `{role}_llm_provider`/`{role}_llm_api_key`/`{role}_ai_model`/`{role}_llm_api_base` — editable via the FastAPI admin, shown in its nav as "Site Configuration" (`can_add=False`/`can_delete=False` singleton in `webadmin/admins.py`; the nav links to the one-row list, click Edit to open `/admin/siteconfig/1/edit`); `{role}_llm_provider` chooses between OpenAI/Anthropic/Google/Groq/Mistral/Cohere/openai_compatible independently per role, `{role}_llm_api_base` only consulted when that role's provider is `openai_compatible`. `linkedin/llm.py:get_llm_model(role)` is the single factory (`role="expensive"` or `"cheap"`). `conf.py:CAMPAIGN_CONFIG` (timing defaults), `conf.py` browser constants (`BROWSER_*`, `HUMAN_TYPE_*`), `conf.py` schedule constants (`ENABLE_ACTIVE_HOURS` flag, active hours/timezone/rest days), `conf.py` onboarding defaults (`DEFAULT_*_LIMIT`, `DEFAULT_CAMPAIGN_NAME`), `conf.py:FASTEMBED_CACHE_DIR` (persistent model cache, defaults to `<project>/.cache/fastembed/`), Campaign/LinkedInProfile models (editable via the FastAPI admin). `VOYAGER_REQUEST_TIMEOUT_MS` lives in `api/client.py` (constructor default on `PlaywrightLinkedinAPI`). `conf.py:DUMP_PAGES` (default `False`) — enable to save page HTML snapshots for fixture collection.
- **Admin panel (`webadmin/`)**: FastAPI app, separate process from Django (`uvicorn webadmin.main:app`), serving at the same `/admin/` path Django Admin used to. Own async SQLAlchemy layer (`webadmin/models.py`) mirrors the tables Django's migrations own — Django remains the only thing that alters schema (`manage.py migrate`); the mirror must be hand-kept in sync with `crm/models/`, `linkedin/models.py`, `chat/models.py` on future migrations. `webadmin/registry.py:ModelAdmin`/`AdminAction` are the declarative config (list_display/list_filter/search_fields/actions/etc.), one per model in `webadmin/admins.py`, driving the generic list/add/edit/delete/action routes in `webadmin/views.py` — analogous to the old `admin.py`/`crm/admin.py` `ModelAdmin` subclasses, including the same 3 custom bulk actions (`run_now`, `mark_human_takeover`, `resume_ai`). Auth reuses the existing `auth_user` table and Django's password hasher (`django.contrib.auth.hashers.check_password`, via a settings-only `django.setup()` in `webadmin/auth.py` — never used for ORM queries); session is a signed cookie (Starlette `SessionMiddleware`, keyed off `DJANGO_SECRET_KEY`). CSRF is a hand-rolled double-submit cookie (`webadmin/csrf.py`) since Django's `CsrfViewMiddleware` no longer runs. `webadmin/dashboard.py` ports the messages-sent/replies-received/connect-requests-sent/accepted stat tiles that used to live in `linkedin/dashboard.py` + `templates/admin/index.html` (both deleted), plus profiles-scanned/leads-messaged/leads-replied tiles, a per-`LinkedInProfile` "Metrics by Profile" breakdown table (owning account recovered by joining `ChatMessage.object_id` to `Deal.lead_id`/`assigned_profile_id`, since `ChatMessage` has no direct profile FK), and a "Daily Metrics" table (last 14 UTC days, newest first, zero-filled). Connect-requests-accepted has no per-event timestamp anywhere in the schema, so it's shown lifetime-only, not per-day.
- **Deal ownership**: `Deal.assigned_profile` (FK to LinkedInProfile, null while the lead is still in the shared pool) is the record of which account owns a lead. Set by `allocate_ready_deals()` at the connect hand-off, or claimed by `set_profile_state()` on PENDING/CONNECTED. Never moved once the account has reached out.
- **Lazy accessors**: `Lead.get_profile(session)` is a pure live Voyager scrape (no DB caching of the raw dict); `Lead.get_urn(session)` reads the `urn` column and falls back to a scrape; `Lead.get_embedding(session)` lazily scrapes + embeds on first access, then caches the 384-dim bytes on the row. `Lead.embed_from_profile(profile)` reuses an in-hand profile dict to skip the scrape (used by `create_enriched_lead`). `Lead.to_profile_dict()` returns a minimal `{lead_id, public_identifier, url, meta}` dict (no `profile` key). `AccountSession.campaigns` (cached_property, list). `AccountSession.self_profile` (cached_property, re-discovers via Voyager on first access per session — no DB cache).
- **Deal summaries**: `Deal.profile_summary` and `Deal.chat_summary` are lazy, mem0-style JSON fact lists built on demand and updated incrementally. `linkedin/db/summaries.py` is the single boundary — `materialize_profile_summary_if_missing(deal, session)` fires on the first follow-up touch (one Voyager re-scrape per `(lead, campaign)` lifetime), `update_chat_summary(deal, new_messages, *, seller_name)` folds newly-synced ChatMessages into the summary via `reconcile_facts`, which routes new facts through mem0's UPDATE prompt to apply ADD/UPDATE/DELETE/NONE events (no naive append-and-dedup). **Only incoming (lead) messages reach fact extraction** — outgoing seller messages are filtered at the boundary so `chat_summary` stores facts about the lead, never the seller's pitch. A one-sided burst of outgoing messages short-circuits the LLM call entirely. **Identity binding (required):** `extract_facts`, `update_chat_summary`, and `reconcile_facts` all require a `seller_name` kwarg, sourced via `seller_name_from(session)` (first_name from `session.self_profile`, username fallback) and injected into the system prompt so the LLM stops inferring `the lead's name is Diego` from a lead reply like `"Hola Diego, gracias..."`. The mem0 reconcile prompt also receives the binding and is instructed to DELETE stored facts that describe the seller as if they were the lead — so previously-contaminated rows *should* be cleaned up on the next sync that produces a conflicting fact, though this is best-effort (mem0's vendored prompt is example-heavy and the cleanup hint is one prepended sentence). Dormant deals with no new messages stay contaminated until eager cleanup. The follow-up agent consumes `profile_summary + chat_summary + last 6 ChatMessage rows` instead of flat profile fields; its prompt (`follow_up_agent.j2`) carries the same `Me`→`self_name` binding under the verbatim-messages header. The fact-extraction prompt is vendored at `linkedin/db/summaries.py:_FACT_EXTRACTION_PROMPT`; mem0's `DEFAULT_UPDATE_MEMORY_PROMPT` and `get_update_memory_messages` are vendored under `linkedin/vendor/mem0/configs/prompts.py` (mirroring upstream paths so future syncs are a clean diff). No `mem0ai` runtime dependency — avoids qdrant/grpcio/sqlalchemy transitive bloat.
- **Django apps**: `linkedin` (main — Campaign with users M2M), `crm` (Lead with embedding/Deal), `chat` (ChatMessage).
- **Data dir**: `data/` holds cookies, `config.json`, and the fastembed cache. Docker users mount volumes at `/app/data`. The CRM database itself is Postgres (see Database below), not a file in this dir.
- **Database**: Postgres, configured via a single `DATABASE_URL` (e.g. `postgresql://user:pass@host:5432/dbname`, `?sslmode=require` for hosted providers like Supabase/Neon/RDS). `db_url.py` (top-level, pure stdlib) is the single source of truth: `get_database_url()` returns `DATABASE_URL` if set, else assembles one from the `POSTGRES_DB`/`POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_HOST`/`POSTGRES_PORT` fallbacks (defaults match the official `postgres` image). `django_db_config()` yields Django's `DATABASES['default']` dict (sslmode → `OPTIONS`); `sqlalchemy_async_url()` yields a `(postgresql+asyncpg://…, connect_args)` pair (sslmode → asyncpg `ssl` connect arg). Both `linkedin/django_settings.py` (ORM/migrations) and `webadmin/config.py` (admin's async SQLAlchemy engine) import this one helper — neither imports the other's stack. The admin engine (`webadmin/db.py`) is created with `pool_pre_ping=True` + `pool_recycle=300` so pooled connections a remote Postgres (or a proxy/firewall on the network path to it) has idle-dropped are validated and transparently reconnected instead of surfacing as asyncpg `connection is closed` 500s on the first request after an idle spell. Both config functions emit a one-line boot diagnostic to **stderr** (also via the logger) — masked URL / resolved host/db/user/sslmode / source (`DATABASE_URL` env vs `POSTGRES_*` fallback vs explicit arg) — so `make logs` shows which DB each process connected to; stderr because resolution happens at settings-import time, before logging is configured. Both compose files pass `DATABASE_URL` to `app` (defaulting to the bundled `db` service) while the `db` (postgres:16-alpine) service still reads `POSTGRES_*` to initialize itself; point `DATABASE_URL` at a remote host to bypass the bundled db. A healthcheck gates `app` startup. Local non-Docker dev: `make postgres` starts a standalone container on `localhost:5432` (the default when `DATABASE_URL` is unset). Upgrading an existing install that still has data in `data/db.sqlite3`: run `python manage.py migrate_sqlite_to_postgres` once, after Postgres is up and migrated — it dumps the old SQLite data with natural keys (so it resolves correctly against Postgres's own contenttypes/permissions rows and doesn't collide with the auto-created superuser) and loads it into Postgres, keeping the exported JSON in `data/` as a backup. Moving all data from one Postgres to another (e.g. Supabase → Neon/RDS/self-hosted, or hosted → local): `python manage.py migrate_postgres_to_remote --source-url 'postgresql://…?sslmode=require' --target-url 'postgresql://…?sslmode=require'`. Both endpoints are explicit flags: `--source-url` (defaults to the ambient `DATABASE_URL`/`POSTGRES_*`) is read from, `--target-url` (or the `TARGET_DATABASE_URL` env) is written to — every phase runs against dedicated `postgres_source`/`postgres_target` connection aliases so the two DBs are exactly the URLs passed in and nothing depends on how `DATABASE_URL` happens to be set. It dumps the source, migrates the target (as `default` in a subprocess), then **streams** the data into it in-process (the `postgres_target` alias) with live timestamped per-model/heartbeat progress, and verifies row counts; refuses to run if source and target resolve to the same host/port/db, target must be an empty/fresh DB, export kept in `data/` as a backup. Streaming loader is a faithful port of Django's `loaddata` (constraint deferral, deferred natural-key refs, sequence reset) so it stays correct while being legible — the per-row-over-the-network load is inherently slow on a remote link.
- **Docker**: Playwright base image, `BUILD_ENV` arg selects requirements. One container runs three things via `compose/linkedin/start`: the admin panel (port 8000, always up, `uvicorn webadmin.main:app`), the automation daemon (supervised, auto-restarts), and VNC for watching the browser (noVNC on 6080, native VNC on 5900). `local.yml` publishes 8000/6080/5900 and auto-creates a Django superuser from `DJANGO_SUPERUSER_*` env (defaults `admin`/`admin`) — the same `auth_user` row the FastAPI admin logs in against. The daemon and admin web server both connect to the same Postgres `db` service, which handles their concurrent writes natively (no busy-timeout workaround needed, unlike the old SQLite setup).
- **CI/CD**: `.github/workflows/tests.yml` (pytest), `deploy.yml` (build + push to ghcr.io).
